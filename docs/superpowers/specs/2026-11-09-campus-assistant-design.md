# 燕小北校园助手首版设计

2026年11月9日，用户已确认整体交互方案。本文件供书面复核，实施计划在复核后编写。项目定位为北工大校园探索与办事找路的课程原型。事实与来源见[研究记录](../../bjut_campus_research.md#L1)。

## 1. 目标与需求

面向新生和来校访客，以持续对话连接校园空间、生活建议和办事服务。首版使用适配手机与桌面的Web页面，后续App、小程序、展示屏通过终端适配器接入。

| 编号 | 已确认需求 | 首版交付 |
|---|---|---|
| REQ-054 | 北工大各校区、地点、知识与办事对应关系 | 五个现行校区目录，本部重点地点、通州已核实服务点，带来源的事项目录 |
| REQ-055 | 对话驱动界面，Galgame式建议 | DS理解意图，返回受控场景动作，建议共4～6项，含继续追问和自定义 |
| REQ-056 | 位置、时间、天气、地图及导航衔接 | 按需定位、前台更新、来源时间显示、助手内预览和显式外部导航 |
| REQ-057 | 持续主动互动 | 前台可见时先气泡询问，用户回应后进入普通对话，含忙态、冷却与安静环境策略 |
| REQ-058 | 燕小北形象及地点实景 | 中央角色开场、侧边陪伴、地点照片与场景切换 |
| REQ-059 | 可重复课堂演示 | 标明模拟时间、位置和天气，离线固定业务与在线增强共用协议 |

创意验收关注三件事。用户用事情描述需求后能获得办事指引，环境变化能产生克制的主动询问，回答能够连同实景和功能页面一起展开。学校已有同名助手，原创体验通过实测对照记录。[已有系统研究](../../bjut_campus_research.md#L1)

## 2. 首次进入

1. 初始视觉中心为燕小北，人物主动问好。
2. 问好后底部对话框自动出现，用户可打字或使用现有语音输入。
3. 开场语音受浏览器自动播放策略控制，文字和角色状态即时显示，首次手势可启用语音。
4. 校区、位置、同行人、时间和计划通过具体问题自然获取。首屏采用人物舞台与随后出现的对话入口。
5. 对话涉及附近、找路或陪伴时，说明用途并请求定位。拒绝后通过校区、校门或地标选项继续。
6. 控制入口在对话出现后提供声音、陪伴开关、返回舞台和演示设置，保持可发现且低干扰。

## 3. 连续场景交互

人物舞台、对话记录与内容场景是同一页面的三个区域。内容展开时人物让至侧边或角落，主要空间显示内容，对话固定保留。

场景类型包括地点详情、校园地图、路线预览、办事步骤、饮食建议和天气。用户继续提问时保留已确认的校区、目的、预算和口味等本次会话条件，条件改变后增加上下文版本。新对话清空会话条件。

转场由场景协调器一次提交。桌面采用角色侧边与内容主区域，手机采用紧凑角色与可滚动内容，底部输入和选项在安全区域内排布。常规动效目标250～400毫秒，减少动态效果设置下采用即时切换或短淡入。

地点照片通过预加载后淡入，照片未就绪时先显示地点信息和中性背景。旧图片迟到归属旧场景，当前地点依据场景版本校验。照片图注显示地点、校区和来源。远程参观显示“地点预览”，定位确认后才显示到达状态。

## 4. 建议与追问

正式推荐面板总计4～6项，由2～4个有依据的具体建议，加“继续追问”和“自定义需求”组成。选项绑定当前轮次、上下文和明确动作。

饮食示例可按已知候选提供附近食堂、符合预算的校内选择、联网取得的校外餐饮和不同口味选择。每项显示简短推荐理由、依据和状态。真实候选不足时先追问或补查，建议数量由有效资料决定。

“继续追问”展示与当前推荐关联的一条待确认条件。“自定义需求”聚焦输入框并保留用户草稿。用户选择地点或路线后先进入预览，再通过明确按钮调用高德或百度。旧选项点击前校验版本，失效时提示重新获取。

事项消歧采用一次一个问题，可以少于四项。主动气泡的回应与关闭属于邀约操作，正式建议面板仍按上述4～6项组织。

## 5. 事项到空间

`ServiceTask`与`Place`分开维护。一个事项可以有多个校区、人群和办理渠道，一个地点可以提供多类服务。

事项记录保存名称、别名、口语例句、校区和适用人群、前置条件、办理步骤、材料、服务地点、线上入口、有效日期和来源。步骤引用稳定地点ID，用户明确确认后记录本次办理进度。

首个真实事项采用平乐园校园一卡通服务指引。“卡丢了”先区分卡种及挂失、补办目标。已核实办理地点使用2026年10月迁址后的学综楼四层窗口。尚未公开确认的费用、材料、营业时段显示未核验，并附现行官方来源或咨询方式。

“学期签到”“录入”等表达先区分体育课、体测、校园跑或其他事项。不同事项使用各自证据。年度通知保存有效日期，人工服务时间与全天咨询电话分别呈现。

图书馆用途指引覆盖安静学习、找书借还、研讨和公共电脑等已公开服务。研讨室预约资格及访客入馆申请要求随对应卡片展示。校门入校、建筑入内、业务办理三类资格分别维护。

## 6. 前台陪伴

用户开启本次陪伴后，页面可见时接收定位和时间变化。主动规则产生候选气泡，用户回应后转成正式对话。

首个闭环采用饭点附近饮食邀约，其后依次扩展图书馆用途、教学区离开、校门附近饮食。邀请文案遵循证据精度，例如“到饭点了，要看看附近吃什么吗”。学习时间和位置仅提供背景，课表与学习目的通过用户表达获得。

### 候选生命周期

`idle → offered → accepted / dismissed / expired`

气泡保存事件ID、触发条件、上下文版本、关联地点或事项、过期时间。展示气泡阶段独立于正式历史、场景和语音。接受时重新核验条件，再提交普通对话轮次。

用户输入、存在草稿、语音识别、模型等待、正在播报或回听暂停时，候选暂缓。最多保留一个候选，恢复空闲后重新检查。新对话、校区变化、关闭陪伴或进入后台使候选失效。

### 规则初值

以下数值为本项目初值，通过现场测试修订，配置与测试同步维护。

| 条件 | 初值 |
|---|---|
| 饭点 | Asia/Shanghai，11点至13点、17点至19点 |
| 建筑周边位置 | 采集时间30秒以内，精度半径40米以内 |
| 进入与离开 | 由核验后的区域定义，默认进入100米、离开150米 |
| 边界可信度 | 定位精度圆完整落在相应边界内或外，模糊状态保持未知 |
| 停留 | 至少30秒，至少两次间隔20秒的有效采样 |
| 采样不足 | 展示前补取新位置，复核失败则等待或询问 |
| 去重 | 同地点同饭点一次，普通建议至少间隔10分钟 |
| 主动候选有效期 | 60秒，接受时再次校验 |

区域缺少核验坐标时使用用户确认地点或标明的模拟情境。区域重叠时采用“附近”表达。离开教学楼依赖用户确认曾在该楼或连续有效区域观测。恢复前台后重新取位置，重新计算停留与离开状态。

进入图书馆安静模式以用户确认或可信的现场环境确认信息为依据。仅询问图书馆或将其设为目的地时，保留原环境状态。安静模式停止当前外放，后续显示文字与气泡。离开后尊重用户声音设置，历史回答由用户选择回听。

原始位置用于当前上下文判定，首版只保存本次会话必要状态。模型接收当前校区、附近地点、位置可信度和事件，餐饮或导航工具在需要时消费坐标。

## 7. 统一对话与受控工具

沿用Spring Boot及已有模型传输层、检索、会话和语音，在应用内增加有限工具编排。模型通过工具获取地点、事项、用途、天气、餐饮和路线所需信息，应用执行并校验。工具最多三轮，整次请求遵守现有总超时，超时按可用本地资料返回可解释状态。

请求包含对话ID、请求ID、基础上下文版本、输入来源、文本或选项ID，以及不可变的终端上下文快照。输入来源区分普通输入、建议选择和主动邀约接受。

统一结果`AssistantTurn`保存轮次ID、上下文版本、回答文本、可播报文本、场景动作、建议选项、引用和声音策略。离线规则回答与在线模型共用该结构，界面标明当前回答模式。

场景动作采用允许列表。`SHOW_PLACE`、`SHOW_MAP`、`SHOW_ROUTE`、`SHOW_SERVICE_TASK`、`SHOW_DINING`、`SHOW_WEATHER`、`KEEP_SCENE`及`RETURN_STAGE`使用已校验的数据ID。场景参数与文本分别验证，动作未知时保留可用文字并提示场景暂不可用。

工具接口按职责划分为地点查询、事项查询、图书馆用途、天气、餐饮候选和路线预览。UI由组件注册表渲染，图片引用资源ID，导航链接由适配器构造。模型输出作为数据处理。

## 8. 轮次、语音与错误恢复

已有前端请求取消只覆盖客户端，后端历史还需要轮次提交保护。模型调用在会话锁外执行，提交前核验请求和上下文版本。新请求、取消和新对话使旧结果失效，显式重试复用请求身份以避免重复提交。

场景、选项、引用和语音属于同一成功轮次。新回答和用户主动打断可停止旧语音，场景重绘仅更新画面。迟到语音事件通过所属轮次及播放ID隔离，地图拖动和图片加载保持播放状态稳定。

主动气泡采用独立状态，接受之后进入对话生命周期。现有`setActivity`会停止语音，接入时需要保留气泡与语音状态之间的边界。[语音状态实现](../../../src/main/resources/static/js/speech-lifecycle.js#L447)、[会话服务](../../../src/main/java/com/guide/service/ConversationService.java#L78)

失败恢复保留用户草稿、当前已提交场景和可用本地资料。天气标注缓存时刻，定位提示来源与精度，图片失败显示中性背景，模型失败提供本地业务或重试入口。离线样本采用持续可见的演示标识。

## 9. 数据目录

| 对象 | 关键内容 |
|---|---|
| Campus | 稳定ID、名称、别名、地址、状态 |
| Place | 校区ID、名称和别名、分类、父地点、入口与坐标系、坐标核验状态、访问说明、来源 |
| ServiceTask | 事项表达、按校区与人群区分的流程、线上与线下步骤、材料、地点引用、有效日期 |
| KnowledgeItem | 校区与地点或事项引用、正文、来源、发布日期、核验时间、有效状态 |
| SceneAsset | 资源ID、地点ID、实景或示意类型、路径、替代文字、视角、来源、署名、许可与拍摄日期 |
| ContextSnapshot | 时间及来源、终端类型、校区、位置及精度和时点、天气及过期状态、会话偏好、模拟状态 |
| ProactiveOffer | 触发ID、上下文版本、关联地点或事项、文案、有效期、状态 |

首版采用JSON目录与现有加载方式，加入关联完整性、校区一致性和来源验证。现有外部知识文件具有优先级，迁移需识别旧灵山数据并选择校园数据集，管理员修改和重启保持同一数据集。历史内容包以明确标识隔离，校园模式的检索、离线回答与默认身份使用同一套校园目录。

燕小北首版以二维素材和待机、倾听、思考、讲述轻动效接入，角色展示接口保留后续绑定模型的接缝。素材清单记录实际资源来源及许可状态。实景图片先逐张检查内容、视角和可用性，建筑外观与室内分区使用各自资源。

## 10. 位置、天气、餐饮与地图

位置适配器区分浏览器采样、用户确认、固定大屏安装点和课堂模拟。坐标始终携带WGS84或GCJ-02标识，供应商边界统一转换。时间取服务端时钟并按Asia/Shanghai解释，离线设备时钟保留来源。

天气首接Open-Meteo，按校区缓存10～15分钟，显示数据时间、获取时间和是否过期。联调记录国内可达性，国内替代供应商通过同一接口接入。

校外餐饮在有配置且联网时查询地图POI接口，展示实际返回的距离、评分和来源时间。评分缺失显示暂无评分，本次候选内排序保留其含义。校内餐厅公开介绍与团队核实的菜品分别带核验日期。营业状态、菜品、价格和口碑采用各自来源。[供应商资料](../../bjut_campus_research.md#L1)

地图提供校区与地点预览，路线显示其数据精度。已核验入口可交给在线路线服务，示意路线明确标注，步行距离与耗时由实际路网结果提供。缺少建筑坐标时展示地址和地点信息，用户可选择以完整校区地点名称打开外部地图搜索并核对目标。

前端地图凭据与服务端餐饮凭据分别配置。真实定位和联网增强在普通展示界面可辨认，演示模拟使用独立数据源。供应商服务结果的存储按照实际协议实现。

## 11. 课堂场景与首个闭环

普通首屏仍为人物舞台。演示设置位于对话后的控制入口，支持暂停、重放和退出模拟。模拟时间和位置全程可见，退出时清除模拟候选并重新定位。

首个Demo验证三个场景。

1. **卡丢了**。从口语提问开始，确认校区及卡种，展示现行服务窗口、资料来源、办理步骤和地图预览，再显式打开外部导航。
2. **去图书馆**。展示图书馆实景，用途选择后给自习、借还或研讨指引，访客询问附申请规则，用户确认在馆内后进入安静模式。
3. **午饭吃什么**。有效前台位置或标明的模拟位置与时间触发气泡，用户接受后出现含继续追问、自定义的4～6项建议，选中后进入地点与路线预览。

教学区离开和临近校门复用同一事件机制，在饭点闭环通过后加入触发场景。管庄、琉璃井、惠新东街先展示已核实校区卡，内部地点和服务在补足资料后逐项扩充。

## 12. 分阶段实施顺序

每个阶段形成可运行的纵向切片，详细任务由后续实施计划拆解。

| 顺序 | 内容 | 完成证据 |
|---|---|---|
| P0 | 校园目录、事项与来源模型，补卡真实业务切片 | 数据校验、别名消歧、现行迁址覆盖历史地址 |
| P1 | 人物开场、统一轮次、对话场景与实景，DS受控工具 | 离线与联网相同协议、角色移位、图片与选项版本隔离 |
| P2 | 位置、时间、天气、地图预览和导航衔接 | 拒绝定位仍可继续、坐标系校验、数据来源和失败状态 |
| P3 | 前台主动邀约、图书馆用途及静音、课堂模拟 | 主动气泡接受闭环、忙态与冷却、模拟退出和恢复 |
| P4 | 餐饮联网增强及跨校区扩充 | 真实接口字段、缺失评分、第二校区同名地点及不同流程 |

三人可按对话与后端、校园资料与地点服务、前端场景与角色分工。共同依赖先冻结统一轮次、地点ID、事项ID与模拟上下文，再并行实施。
